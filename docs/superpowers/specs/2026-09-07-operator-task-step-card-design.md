# 检测站任务页 · 本步任务卡（方案 B）

**日期：** 2026-09-07  
**状态：** 已确认，待实现  
**范围：** 微信小程序检测站端 `packages/operator/pages/operator-detail`（检测任务详情）

## 问题

检测站管理员打开任务后，页面在多个业务状态下外观接近，难以判断：

1. 当前停在流程的哪一步  
2. 底部主按钮按下去会推进什么、不等于什么  

现有「服务流程」五格图标条信息密度高但区分度弱；核验清单与履约时间线更像证据区，不承担「当前该点什么」。

## 目标

在任务详情页一眼回答三件事：

- **我在哪一步**（步骤名 + N/5）  
- **这一步要做什么**（1–2 句）  
- **主按钮按了会怎样 / 不等于什么**（按钮文案 + 可选灰字边界说明）

成功标准（已选 C 的组合）：步骤标识 + 按钮意义文案同时具备。

## 非目标

- 不重做履约时间线视觉（审计流水仍保留原列表）  
- 不改车主端「年检问题处理」页  
- 不改变后端状态机与 action API 语义，仅改呈现与文案  
- 本轮不做吸底固定栏（方案 C）；若现场反馈「边看照片边点」再加

## 方案

采用方案 **B · 本步任务卡置顶**：

1. **替换**现有 `process-card` / `process-steps` 五格 UI 为「本步任务卡」  
2. **保留**车牌头图区、到站留证、到站核验清单、媒体、履约时间线、系统边界说明  
3. **改写**各状态主按钮文案，并在按钮下增加一行边界说明（有动作时）

### 任务卡结构

| 字段 | 说明 |
|------|------|
| `stepIndex` / `stepTotal` | 展示为 `本步任务 · N / 5` |
| `title` | 当前步骤名 |
| `instruction` | 本步要做什么 |
| `nextLabel` | `完成后进入：…`；终态可改为「本单已结束」等 |
| `primaryLabel` | 主按钮文案；无主按钮时为空 |
| `primaryHint` | 按钮下灰字；无按钮时可为等待说明 |

五步序号与现有 `processSteps` 对齐：

1. 预约确认  
2. 到站核验  
3. 交接检测  
4. 结果回传  
5. 服务完成  

### 状态 → 卡片 / 按钮映射

| `booking.status`（及条件） | N | title | instruction（草案） | nextLabel | primaryLabel | primaryHint |
|---------------------------|---|-------|---------------------|-----------|--------------|-------------|
| `confirmed` 自驾 | 1 | 预约确认 | 确认接单，等待车辆按预约到站。 | 完成后进入：到站核验 | 接单并等待到站 | 接单后订单进入待到站，不会自动完成核验 |
| `confirmed` 代驾 | 1 | 预约确认 | 支付已确认，等待后台安排司机。 | 完成后进入：到站核验 | （无，只读提示） | 等待司机任务下发后再继续 |
| `awaiting_arrival` / 部分 `picked_up` | 2 | 到站核验 | 核对实车车牌与预约资料，确认车辆已到站。 | 完成后进入：交接检测 | 确认到车 · 核验通过 | 不等于开始检测，仅标记到站完成 |
| `checked_in` | 3 | 交接检测 | 确认车辆可进入检测线，交给检测流程处理。 | 完成后进入：结果回传 | 确认交接 · 开始检测 | 之后请在设备侧检测，再回小程序填报告 |
| `inspecting` | 4 | 结果回传 | 补齐现场照片与年检结论，生成体检报告并同步车主。 | 完成后进入：服务完成 | 填写体检报告并回传 | 未完成报告前，订单会停在「检测中」 |
| `result_received` + legacy | 4 | 结果回传 | 历史遗留单需手工收尾。 | 完成后进入：服务完成 | 完成历史遗留服务 | 确认后订单将标记为已完成 |
| `returning` 代驾 | 5 | 服务完成 | 车辆送回中，最终送达与留证由本单司机完成。 | 本单收尾中 | （无） | — |
| `completed` | 5 | 服务完成 | 结果已同步给车主。 | 本单已结束 | （无） | — |
| `on_hold` | 保持挂起前步骤序号 | 异常挂起 | 车辆信息不一致，现场复核完成后再恢复。 | 恢复后回到挂起前步骤 | 异常已处理，恢复核验 | 恢复后请继续完成当前步骤主操作 |

预检「等车主处理」等若出现在站端详情且无站内主操作：任务卡 `title`/`instruction` 说明等待原因，主按钮隐藏；不另开页。

挂起次按钮文案可保持「车辆信息不一致，挂起复核」，本规格不强制改。

### 关键三步定稿文案（已确认）

| 步骤 | 按钮 | 防误点说明 |
|------|------|------------|
| 到站核验 | 确认到车 · 核验通过 | 不等于开始检测，仅标记到站完成 |
| 交接检测 | 确认交接 · 开始检测 | 之后请在设备侧检测，再回小程序填报告 |
| 结果回传 | 填写体检报告并回传 | 未完成报告前，订单会停在「检测中」 |

## 实现要点

**文件（预期）：**

- `operator-detail.ts`：用 `currentTaskCard(booking)`（或等价）替换/扩展 `processSteps` 输出；为每个可操作态提供 `primaryLabel` / `primaryHint`  
- `operator-detail.wxml`：去掉五格 `process-steps`；插入任务卡；主按钮区展示 `primaryHint`  
- `operator-detail.wxss`：任务卡样式（沿用站端蓝白体系，避免新色板）

**行为约束：**

- `data-action` 与现有 `accept` / `check-in` / `handoff` / `hold` / `resolve-hold` / `complete` 及 `openCheckupEditor` 不变  
- `currentStepIndex` 逻辑可复用，仅改变渲染形态  
- 无障碍：任务卡标题与按钮文案应能被读屏读到「当前步骤」语义（可用既有 `aria-label` 增强，非必须新 API）

**测试建议：**

- 对 `currentTaskCard`（或纯函数映射）做表驱动单测：覆盖上表主要 status  
- 真机/开发者工具目测：到站核验 → 交接检测 → 结果回传三态卡片与按钮是否一眼可辨

## 验收

1. 打开处于「待到站核验」的任务：顶部可见「到站核验」任务卡，主按钮为「确认到车 · 核验通过」，下方有不等于开始检测的说明。  
2. 推进到 `checked_in` 后：卡片变为「交接检测」，按钮变为「确认交接 · 开始检测」。  
3. `inspecting`：卡片为「结果回传」，按钮进入报告编辑。  
4. 页面中部核验清单/时间线仍在；不再展示原五格流程条。
