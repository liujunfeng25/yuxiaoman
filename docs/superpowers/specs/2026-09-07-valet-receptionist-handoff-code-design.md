# 年检代驾：接待人联系方式 + 取车抢码 + 换人发新码

日期：2026-09-07  
状态：已确认（含换人二次确认；可写实现计划）

## 背景

年检代驾当前后台「一单一司机任务验证码」流程要求运营填写**司机姓名/电话**并生成 6 位码；代驾端输入码后绑定订单。实际协作是：取车码发到线下微信群抢单；站点侧需要稳定的接待人联系方式；取送可能换人，换人应在**送达检测站后由取车代驾主动点「换人」**再发新码，而不是复用取车码。

## 目标

1. 后台生成取车验证码时，填写**检测站接待人员姓名与电话**（不再填司机）。
2. 代驾端订单详情可看到接待人电话，便于联系站点。
3. 代驾输入验证码成功后：将微信身份写入**客户中心**并标明角色/标签为**代驾**；再**手填手机号**后才能进入订单。
4. 取车代驾手机号写入订单，在**客户端 / 检测站端**订单详情展示为**取车代驾联系方式**。
5. **取车阶段验证码一人绑定**：群里谁先成功输入就是谁的；绑定后原码不可再被他人使用。
6. **同一人继续送车**：不点换人，沿用已有司机会话与流程。
7. **换人送车**：取车代驾送达检测站后，在代驾端点击「换人」→ 生成**新的换班/送车验证码**（**仅代驾端展示可复制**）→ 线下交接 → 接班司机输入新码 → 存微信（代驾）+ 手填手机 → 进入订单，记为**送车司机**；联系方式展示在检测站端与客户端；**原取车代驾立即失去该单后续操作权**。

## 非目标（本期不做）

- 微信「手机号快速验证」组件（本期仅手填 11 位手机号）。
- 取车进行中允许多人争用同一成功码，或送达后复用取车码认领送车。
- 以运营后台作为换班码的主发放入口（后台最多只读/应急作废，不挡主路径）。
- 拆成两套独立 `assignment`（取车单/送车单完全分离）。
- 改变代驾四组五图留证推进本身（仅改认领、联系人与换人入口）。

## 已拍板决策

| 项 | 决策 |
| --- | --- |
| 后台联系人字段 | 检测站接待人员姓名 + 电话 |
| 手机号采集 | 手动输入 11 位 |
| 取车码 | 群内先到先得，一人绑定后作废 |
| 同人送车 | 不点换人，原会话继续 |
| 换人 | 送达站后由代驾端「换人」生成**新码**；点击后须**二次确认**才生成 |
| 换班码可见性 | **仅代驾端**点换人后展示/复制（可选后台只读应急） |
| 换人后原司机 | 立即失去后续操作权 |
| 实现骨架 | 一单一凭证 + `pickupDriver` / `returnDriver` 两段执行人 |

## 用户流程

### A. 运营安排取车

1. 订单处于可安排代驾状态。
2. 运营填写接待人姓名、电话，生成取车 6 位验证码。
3. 将码发到线下微信群。

### B. 取车代驾认领

1. 打开代驾端，输入取车码。
2. 系统校验：码有效且尚未绑定 pickup。
3. 用当前微信登录身份写入/更新客户中心档案，标记为代驾。
4. 强制手填并确认手机号。
5. 绑定为 `pickupDriver`，签发司机会话，进入订单。
6. 取车码标记为已消费/不可再绑。

### C. 同人送车

1. 取车履约完成（送达检测站）后，若未点「换人」，原司机继续可见可操作送车任务。
2. `returnDriver` 与 `pickupDriver` 为同一人（或逻辑等价：未单独绑定 return）。

### D. 换人送车

1. 前置：取车已送达检测站（与现有「送达站」状态对齐，实现时钉死具体 status/事件）。
2. 取车代驾在代驾端点击「换人」。
3. **必须二次确认**（弹窗说明：将生成新换班码、原司机在接班人绑定后失去操作权等），确认后才生成码；取消则不生成。避免误触。
4. 系统生成新的 6 位换班码，在代驾端展示（可复制）；原取车码不可用于新人。
5. 线下将换班码交给接班司机。
6. 接班司机输入换班码 → 客户中心（代驾）→ 手填手机 → 绑定 `returnDriver`。
7. 吊销原取车代驾对该单的会话/操作权。
8. 车主端、检测站端展示送车司机联系方式。

## 数据模型（逻辑）

### 任务凭证（挂在现有 `valet_driver_assignments` 或等价表上扩展）

- `receptionistName` / `receptionistPhone`：接待人（原司机姓名电话字段改义或新列，实现计划中选定迁移方式）。
- `pickupVerificationCode`：取车码（哈希存储；绑定后失效）。
- `handoffVerificationCode`：换班码（点「换人」后生成；绑 return 后失效）。
- 码的过期、失败限流沿用现有代驾验证码策略（按微信用户与来源 IP）。

### 执行人

- `pickupDriver`：`userId`、客户中心引用、手机号、`boundAt`。
- `returnDriver`：可空；换人绑定后写入；同人送车时等于 pickup 或不单独占用换班码。

### 客户中心

- 代驾微信用户落客户档案，角色/标签明确为「代驾」，与车主角色区分。
- 手机号以认领时手填为准，写入对应执行人字段，并可供订单详情展示。

## 各端展示

| 端 | 展示 |
| --- | --- |
| 运营后台 | 接待人；取车码（生成时）；换班码可不作为主 UI，至多只读/作废 |
| 代驾端 | 接待人姓名/电话；认领后本单任务；送达后「换人」与换班码 |
| 客户端订单详情 | 取车代驾联系方式；若已绑定送车司机则另显送车联系方式 |
| 检测站端订单详情 | 同上，便于验完联系代驾取车/交接 |

## 状态与权限要点

- 取车码：未绑定可抢；绑定成功后对他人永久拒绝（直至运营应急重发取车码，若保留该能力）。
- 换班码：仅在「已送达站且已点换人、尚未绑定 return」窗口有效。
- 换人绑定成功：原 pickup 会话对该 booking 失效，避免双人同时推进送车。
- 未送达站：代驾端不展示「换人」，或不允许生成换班码。

## 风险与边界

- 手填手机号可能填错：UI 需格式校验与二次确认（实现计划细化）。
- 换班码仅司机端可见：丢失时可再次点「换人」重新生成（使旧换班码作废）——若采纳，需在实现计划写明；**定稿默认允许重新生成换班码并作废未使用的旧换班码**。
- 微信昵称/头像能力受小程序政策限制：客户中心至少保存稳定 `openid`/`unionid`（若有）与会话用户 id；昵称头像能取则取，不能取不阻塞认领。

## 验收标准

1. 后台安排入口为接待人字段 + 取车码，无司机姓名电话必填。
2. 两名用户竞争同一取车码，仅一人绑定成功，另一人失败提示明确。
3. 绑定流程强制手填手机后才能看到订单详情/任务。
4. 客户中心出现该用户且标明代驾。
5. 车主/检测站订单详情可见取车代驾电话；代驾端可见接待人电话。
6. 未送达站无法生成换班码；送达后点换人须二次确认，取消不生成；确认后仅代驾端可见新码。
7. 接班司机用换班码进入后成为送车司机，原司机无法再操作；两端详情可见送车联系方式。
8. 同人送车不点换人可完整走完送车流程。
